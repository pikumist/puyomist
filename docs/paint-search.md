# 前段「ぷよ塗り」探索の設計と実測

なぞり消しの前に、任意のマスを1色に塗り替えて連鎖しやすい盤面を作り、そのあとで
なぞり消しの良い値（ぷよ使いカウント／ダメージ量／スキル溜め数）を狙う。
その**前段の塗り案を探索する方式**を決めるための調査記録。

> 方針: **推測するな、計測せよ**。採用・却下はすべて実測に基づく。
> 計測用バイナリは `packages/solver-wasm/src/bin/paint_*.rs`、
> 共有ロジックは `packages/solver-wasm/src/paint.rs`。

---

## 1. 問題設定

| 項目 | 内容 |
|---|---|
| 塗りの形 | 連結不要。盤面の任意のマスを指定色に塗り替える |
| 塗り色 | 1色固定（ユーザーが指定） |
| 塗り上限 | ユーザーが指定。通常 8 か 10 |
| 塗れるマス | 色ぷよ / ハート / おじゃま / 固ぷよ |
| 塗れないマス | プリズム、?ぷよ、ネクスト、既に塗り色と同色の色ぷよ（塗っても盤面が変わらない） |
| ハード制約 | **塗り後に1つも消えないこと** |
| 多段塗り | 1段ずつ人が確定していく運用。実装は1段分でよい |

プラス／チャンスは塗り替え後も維持される（`convertPuyoType` / `convert_type` が対応済み）。
固ぷよ・おじゃま・ハートは塗ると色ぷよになる。

---

## 2. ハード制約は単調で、有効解だけを直接列挙できる

塗りで増えるのは塗り色だけで、他色は減るだけなので新たに消えることはない。よって
「塗り後に1つも消えない」は次と等価。

> 塗り後、塗り色の連結成分（4近傍）がすべて `minimum_puyo_num_for_popping - 1` 個以下

塗りマスを追加すると塗り色の集合は単調増加するので、**S が違反なら S の上位集合もすべて違反**。
つまり有効な塗り集合は下方閉であり、増分DFSで有効なものだけを列挙できる。

これが効く。8×6=48マス・上限10マスの部分集合は約87億通りあるが、実際に列挙されるのは
最悪でも1.8億通りで、**1件あたり約9ns**（最悪ケースが単スレッド1.6秒）。
「全部作ってから捨てる」のではなく最初から有効なものだけを生成するため、**列挙は事実上無料**。

実装は `paint.rs` の `PaintSetup::for_each_paint_set`。増分DFSの結果が
独立実装の総当たりと完全一致することをテストで担保している。

## 3. 候補マスの絞り込み

ハード制約とは別に、候補マス自体を削るヒューリスティック（`PaintFilter`）。
距離は4近傍のマンハッタン距離、基準は初期盤面の塗り色の位置。

| filter | 内容 | 判定 |
|---|---|---|
| `all` | 絞り込みなし | **採用（既定）** |
| `adj1` | 塗り色に距離1以内 | 却下 |
| `adj2` | 塗り色に距離2以内（1マス飛ばしの橋渡しを含む） | **却下** |
| `dead` | そのままでは絶対に消えないマスのみ | 却下 |
| `adj2dead` | `adj2` かつ `dead` | 却下 |

### 結論: 絞り込みは不要（一度 `adj2` を採用してから撤回した）

**絞り込みは全数列挙が前提だった頃の設計**である。候補を9,600万件から130万件に削る必要があった段階では
必須だったが、ビームサーチ（§7）に切り替えた時点でコストは候補**総数**ではなく候補**マス数**
（＝分岐数）にしか依存しなくなり、絞り込みの存在理由が消えた。

`all` にしてもコストは 1.4 倍にしかならない一方、`adj2` は**最大 22.9% 取りこぼす**。

| 組 | adj2/幅300 | adj2/幅1000 | all/幅300 | **all/幅1000** |
|---|---|---|---|---|
| seed1 赤 | 234 | 234 | 243 | **243** |
| seed1 黄 | 198 | 198 | 210 | **210** |
| seed2 赤 | 183 | 183 | 225 | **225** |
| seed2 黄 | 222 | 222 | 228 | **237** |
| seed3 青 | 228 | **234** | 210 | 228 |
| seed3 緑 | 240 | — | 243 | **243** |

`adj2` が落とすのは「既存の塗り色が全く無い領域に、塗りだけで新しい種を作る案」と
「距離2のマスを足がかりにさらに外へ伸ばす案」である。塗るマス**同士**の距離は見ていないので、
遠く離れた2マスを塗る案自体は `adj2` でも見つかる。

`all` は候補マスが増える分ビームが薄まるため、**幅を広げる必要がある**（幅300では seed2黄 228 /
seed3青 210 だったものが、幅1000で 237 / 228 に改善）。

> **注意**: §6・§7 に載せた「到達率1.000」は、`adj2` で絞った集合の中での全数列挙を真値とした
> 数字である。その真値自体が `all` の解より最大 22.9% 低いので、**あの1.000は「狭い箱の中で満点」
> という意味しかない**。`all` の真の最適値は全数列挙が 87 億通りで測れないため未知。

### `adj1` の却下理由

塗りマス同士が隣接して4連結してしまうため、**塗り10マスが原理的に置けなくなる**。
なつアマ/1 の黄では最大4マス、緑では最大5マスしか置けず、最も価値が高い
「上限いっぱい塗る」領域を丸ごと捨ててしまう。

### `dead` の却下理由

「そのままでは絶対に消えない」マス（後述）だけに絞ると候補は 7〜2,399 件まで落ちる
（`adj2` の1万〜9,600万件から3〜7桁の削減）。しかし最良値の **20〜39% を取り逃す**。

| 組 | `adj2` 真値 | `dead` | 比率 |
|---|---|---|---|
| seed1 赤 | 234.0 | 192.0 | 0.821 |
| seed1 黄 | 198.0 | 150.0 | 0.758 |
| seed2 赤 | 183.0 | 111.0 | 0.607 |
| seed2 黄 | 222.0 | 216.0 | 0.973 |

死にマスは「元の色が孤立している」＝盤面の中で他と繋がっていない位置なので、
そこを塗っても塗り色が繋がりにくい。**「塗って損しない」と「塗って得する」は別物**だった。

### `adj2` での候補数（ランダム通常盤面・上限10）

| seed | 赤 | 青 | 緑 | 黄 | 紫 |
|---|---|---|---|---|---|
| 1 | 103,022 | 906,663 | 12,781,752 | 89,174 | 1,498,098 |
| 2 | 10,613 | 594,061 | 12,855,921 | 360,241 | 4,642,036 |
| 3 | 772,008 | 578,090 | 96,082,484 | 2,838,139 | 951,529 |

色によって4桁の幅がある。**盤面上にその色が少ないほど制約がゆるく候補が爆発する**。

## 4. 却下した枝刈り: 列のランによる支配判定

落下は縦方向のみでぷよの列は不変なので、隣接し得るのは列差1以内のぷよ同士に限られる。
よって連結成分は「その色が1個以上ある列の連続区間（ラン）」の中にしか収まらず、

> ランに含まれるその色の総数が最低消し数未満なら、そのラン内のぷよは絶対に消えない

が厳密に成り立つ（`paint.rs` の `ColumnRuns`）。

**注意**: 「あるマスを中心とした横±1マスの窓」で判定するのは**誤り**。連結成分は列をまたいで
数珠つなぎに伸びられるため、列ごとの個数が 0,1,1,2 のとき窓の合計は2でもランは4になる。

### 却下理由

厳密だが、**ランダム通常盤面ではほとんど刈れない**（通過率 80.6〜100.0%、中央値98%）。
48マスに5色なので1色あたり平均9〜10個あり、ある列（6マス）にその色が無い確率は
(4/5)⁶ ≈ 26%。平均8列中2列しか欠けないのでランがほとんど分断されない。
最大の問題児だった seed3 緑も 9,608万 → 7,744万 で、評価コストの桁が1つも下がらない。

### 残した価値

規則自体は厳密なので、**UI で「このぷよはそのままでは消せません」と表示する**用途に使える
（`paint.rs` の `dead_cells`、計算は数マイクロ秒）。2000盤面での実測で
**1盤面あたり平均7.02個・最大19個・99.9%の盤面に1個以上存在**する。

> **厳密なのは限定条件下だけ**。この判定は「列ごとのその色の数は増えない」ことを前提にしており、
> 次の場合は成り立たない。UI 文言にするなら「今の盤面のなぞり1回では」等の限定が要る。
> - `TraceMode::To*`（なぞり塗りモード）: なぞりが任意のセルをその色に変えるので加算される
> - 不確定ぷよの補充を有効にした場合（§8）: 任意の色が降ってくる
> - 実際のゲーム: 補充は無制限に降ってくるので、連鎖後半では偽になり得る

## 5. 却下した代理評価: 静的スコア

探索を1回も走らせず、塗り色の連結成分の形だけから点を付ける関数。
成分サイズ 1個=1点 / 2個=4点 / 3個=12点で合計する
（制約により成分は最大3個。3連結は「あと1個で発火」なので高く評価する狙い）。

**全5組で失格**。Spearman 0.04〜0.40、緑ではマイナス0.32。
上位100件に絞っても真の最良値の 0.82〜0.92 にしか届かない。

理由は**位置関係を一切見ていないこと**。「3連結が2つ」でも、1回のなぞりで両方に火を付けられる
配置と、盤面の端と端で絶対に繋がらない配置が同点になる。連鎖の良し悪しは種の数ではなく
位置関係で決まる。

## 6. 採用した代理評価: なぞり数を落とした全探索

本番評価は「なぞり6の全探索」（1件2ms）。代理として、なぞり数を落とした全探索を使う。

| 代理 | 1件あたり | 対 本番比 |
|---|---|---|
| なぞり5 | 0.48 ms | 4.7× 安い |
| **なぞり4** | **0.093 ms** | **23× 安い** |
| なぞり3 | 0.019 ms | 121× 安い |
| 静的スコア | 0.00003 ms | （実用外） |

`screen@N` = 代理の上位N件だけを本番評価したときに得られる最良値 ÷ 真の最良値。

| 盤面/色 | 候補数 | 塗り利得 | trace=3 @100 | trace=4 @100 | trace=4 @500 |
|---|---|---|---|---|---|
| seed2 赤 | 10,614 | 2.10× | 0.951 | 0.951 | 0.967 |
| seed1 黄 | 89,175 | 2.13× | 1.000 | 1.000 | 1.000 |
| seed1 赤 | 103,023 | 2.52× | 1.000 | 1.000 | 1.000 |
| seed2 黄 | 360,242 | 2.55× | 1.000 | 1.000 | 1.000 |
| seed3 青 | 578,091 | 2.23× | 0.872 | 0.936 | 1.000 |

**なぞり3は却下**。seed3 青では上位1000件まで広げても0.910で頭打ちになる。
**なぞり4を採用**。上位500件で全組が真の最良に到達する。

## 7. 採用した探索: ビームサーチ

代理評価が23倍安くても、候補9,600万件に全掛けすると2.5時間かかる。
ビームサーチなら評価回数が**候補総数に依存せず**、深さ × ビーム幅 × 分岐で決まる。

根拠は、全数列挙の真値で `best_by_paint_size` が塗り数に対して単調増加していたこと
（例: 93→144→171→180→192→213→219→234）。最適な塗り数は7〜8個で、
9〜10個ではむしろ悪化する例が3組あった。

### 手順

1. 空集合から始め、深さごとに候補マスを1つ足した集合をすべて作る
2. ハード制約を満たすものだけ残す
3. 代理評価（なぞり4）で並べ、上位 K 件だけ次の深さへ
4. 全深さのビーム内容から代理上位 3K 件を本番評価（なぞり6）して最良を採る

### 到達率（全数列挙の真値に対する比）

| 設定 | 平均 | 最小 | 所要 |
|---|---|---|---|
| 幅100 / 検証500 | 0.982 | 0.910 | 1.3〜1.7秒 |
| 幅300 / 検証2000 | 0.995 | 0.974 | 4.4〜6.1秒 |
| 幅1000 / 検証3000 | **1.000** | **1.000** | 6.6〜11.5秒 |

**幅を広げるときは検証数も一緒に広げること**（目安は検証数 ≒ 幅×3）。
検証数を500に固定したまま幅だけ300に広げると、代理の並びで真の最良が押し出されて
seed2赤が 1.000 → 0.967 に**悪化**した。

### 最悪ケース

seed3 緑（全数列挙 96,082,484 件、代理を全掛けして2.5時間）:

| ビーム幅 | 最良値 | 所要 |
|---|---|---|
| 100 | 237.0 | 1.9秒 |
| 300 | 240.0 | 5.4秒 |
| 1000 | 240.0 | 16.4秒 |

**2.5時間 → 5.4秒**。幅300と1000が同じ値に収束している。

## 8. 不確定ぷよの確率的評価

シミュレータはネクストが落ちたあとの空きマスを埋めない（TS は ?ぷよで埋める。
どちらも消えないので連鎖はそこで止まる）。実際には色ぷよが降ってきて連鎖が伸び得るので、
決定論評価は系統的な過小評価であり、実際の結果は確率的にブレる。

`SimulatorBB` の `UnknownFillPolicy` で切り替える。既定は `Inert`（従来挙動）。

| policy | 内容 |
|---|---|
| `Inert` | 補充しない（既定・過小評価側） |
| `ChainAverse` | ランダムだが**補充ぷよ同士を隣り合って同色にしない**。補充だけでは発火せず、既存の塊を伸ばす効果だけが残る |
| `Random` | 一様ランダム。補充ぷよが固まって自力発火し得る（過大評価側） |

### 実測（`ChainAverse`、補充2回まで、40サンプル）

| 盤面/色 | 決定論最良 | 期待値 | 伸び | 決定論1位の期待値順位 | 1プレイのばらつき | 上位30案の幅 |
|---|---|---|---|---|---|---|
| seed1 赤 | 234 | 271.3 | 1.16× | 16位 | ±16.5 | 21.8 |
| seed1 黄 | 198 | 251.8 | 1.27× | 3位 | ±20.1 | 26.5 |
| seed2 赤 | 183 | 217.8 | 1.19× | 7位 | ±20.9 | 25.3 |
| seed2 黄 | 222 | 268.6 | 1.21× | 8位 | ±14.9 | 29.5 |
| seed3 青 | 213 | 272.8 | 1.28× | 1位 | ±20.3 | 37.4 |

**1回の実プレイのばらつき（±15〜21）が、上位30案の期待値の幅（22〜37）と同程度**。
案Aと案Bのどちらが良いかは、実際に打てば運で簡単に逆転する差しかない。
決定論の最適解を厳密に追うのは過剰適合になる。

### 効くのは「最終並べ替え」だけ

| | seed1赤 | seed2黄 | seed3青 |
|---|---|---|---|
| ① 決定論値の1位をそのまま採る | 271.3 | 268.6 | 272.8 |
| ② 決定論ビームの候補を**期待値で並べ直す** | 280.8 (+3.5%) | 278.9 (+3.8%) | 272.8 (+0%) |
| ③ さらに**期待値でビームサーチ**する | 281.7 (+0.3%) | 278.9 (+0%) | 274.2 (+0.5%) |

期待値ビームでしか到達できない塗り案は3組中2組で実在したが、その差は 0.3〜0.5% しかない。
コストは10倍（代理評価 4,988回 → 39,824回）。**探索は決定論のまま、選抜だけ期待値にする**のが正解。

理屈も通っている。決定論評価と期待値は伸びが一律1.2倍前後で強く相関しているので、
良い案の集合はほぼ同じ。違うのは団子になった上位の中での並び順だけ。

期待値でサンプリングするときは**共通乱数法**（全候補に同じ補充パターン列を当てる）を使うこと。
1案あたりの標準偏差は ±15〜21 ある一方、隣接候補の期待値の差は 1〜3 しかないため、
独立サンプリングでは順位が雑音に埋もれる。

### 偏り（bias）と分散（variance）は別物

**サンプル数を増やして減るのは分散だけで、偏りは何回サンプリングしても同じ方向にズレ続ける。**
`ChainAverse` の実装では当初この区別を誤り、次の3つの偏りを作り込んでいた（いずれも修正済み）。

| 偏り | 内容 | 修正 |
|---|---|---|
| 色の押し出し方向 | 衝突時に色番号を +1 する実装だと、隣接ペア (c, c+1) が他の1.6倍出やすくなる。周辺分布は巡回対称性で一様のままだが、同時分布が歪む | 許される色から**一様に**選び直す |
| 走査順の空間的非対称 | ビット番号昇順で走査すると、先に処理される右下のマスほど制約が少なく自由になる。盤面の左右で色の決まり方が変わる | サンプルと補充回ごとに**割り当て順をシャッフル**（偏りを分散に変換したので、以後はサンプル数が効く） |
| 補充回をまたぐ色の再利用 | 色をビット位置だけで引くと、2回目の補充が1回目と同じ位置に同じ色を置く。「消えた場所に同じ色がまた降って同じ塊を再形成する」軌道が過剰になる | 乱数種に**補充回数を混ぜる** |

修正の前後で結論は変わらなかった（決定論の過小評価 1.16→1.22倍、決定論1位を選んだときの
取りこぼし 0.978→0.964、順位の入れ替わりも継続）。また `ChainAverse` と、偏りを持たない
`Random`（衝突解決をしないので上記の問題が原理的に生じない）の**両極端で同じ結論**が出ている。

## 9. 計測条件（重要）

結論は盤面・色・評価基準で簡単に逆転する。以下を外すと誤った結論に至る。

### 特殊盤面で測ってはいけない

`src/logics/boards` の盤面（chainSeed1/2, specialRule1〜6）はすべて連鎖が仕込まれた特殊盤面。
そこで測ると **ぷよ使いカウントでは塗りの利得が 1.00〜1.02×** になり「塗りは無意味」という
誤った結論が出る。実運用は連鎖しない通常盤面を塗りで連鎖させるので、
**通常盤面（ランダム生成）で測ること**。通常盤面では利得 2.10〜2.55×。

### ランダム盤面は初期消えなしの棄却サンプリングが必須

完全ランダムだと **82.5% が「いきなり消える」不正な盤面**になる（500盤面で平均試行回数5.7）。
実際のゲームの初期盤面には存在し得ない状態であり、塗りのハード制約の前提とも矛盾する。

生成条件（実運用の申告に合わせた既定値）:
色ぷよ5色を一様ランダム / ハート 0〜3個 / チャンスぷよ 0〜2個 / プラスぷよ 0〜48個 /
プリズム・固ぷよ・おじゃまは無し。

### ブーストエリア全面は順位に影響しない

`calc_puyotsukai_count` は「エリア外プラス×2 + エリア外通常×1 + エリア内プラス×6 + エリア内通常×3」。
全面ブーストだと一律3倍になるだけで最適解は変わらない。**部分エリアなら影響する**。

### 優先度は実運用の順で

チャンス → 値が大きい → プリズム → 全消し → なぞり数が少ない。
ただし組み込み盤面にチャンスぷよは存在しないため、チャンス優先は同点になり
「値が大きい」が先頭に来るのと挙動が一致する。

---

## 10. 結論としての方式

```
1. 候補マスは絞らない（絞ると最大 22.9% 取りこぼす。コストは1.4倍にしかならない）
2. 決定論のビームサーチ（幅1000、代理 = なぞり4の全探索）            5〜11秒
3. 全深さのビーム内容から代理上位 3K 件を本番評価（なぞり6の全探索）  6〜7秒
   ※「塗らない」案は代理スコアを持たないので、無条件で検証対象に加えること
4. [任意] 上位N件を期待値で並べ直す（ChainAverse）                  最大 +3.8%
5. 人が塗り案を1つ選ぶ → 盤面に適用 → 後段は既存の全探索をそのまま
```

計算量が候補総数に依存しないため、盤面がどれだけ極端でも十数秒で終わる
（全数列挙だと代理評価だけで2.5時間かかる盤面がある）。

## 10.1 実装上の落とし穴

- **`better_solution` は全順序ではない**。完全同点のとき第1引数を返すため、比較関数として
  そのまま使うと `cmp(a,b)` と `cmp(b,a)` が両方 `Less` になり、反対称性が壊れる。
  値は実質整数（ぷよ使いカウント等）なので同点は普通に発生し、Rust 1.81 以降の `sort_by` は
  これを検出すると panic する。両方向を呼んで同点判定すること（`paint_search.rs` の `build_plans`）。
- **「塗らない」案は代理評価を通らない**ので、上位選抜に任せると消える。塗りがすべて損な盤面では
  これが答えになるため、無条件で本番評価に加えること。

## 10.2 wasm でのワーカー分割

wasm は単スレッドで、1関数で完結させると標準精度 (幅300) でも約19秒かかる。その間 UI が
固まるので、段ごとに分けて公開してある。

| wasm 関数 | 役割 | 重さ |
|---|---|---|
| `paint_expand_beam` | ビームを1段展開 | 軽い (分割不要) |
| `paint_evaluate_sets` | 塗り集合をまとめて評価 | **ここだけが重い。JS が分割する** |
| `paint_select_top` | 上位K件の添字 | 軽い |
| `paint_build_plans` | 良い順に並べて塗り案にする | 軽い |

JS 側 (`src/logics/paint-search-worker-driver.ts`) が深さごとに
「展開 → 評価をNワーカーに配る → 集約 → 上位K件」を回す。

> **分割した評価は必ず元の順序で組み直すこと**。順序が崩れると同点の並びが変わり、
> Rustネイティブバックエンドと結果が食い違う。この手順が逐次版
> (`search_paint_plans_with`) と完全に一致することは、ワーカー数を変えて突き合わせる
> `split_evaluation_matches_sequential_search` テストで担保している。

## 10.3 Rustネイティブバックエンド

`solver-server` に `{type:"paint"}` を追加した。ワイヤープロトコル:

```
client -> server: { type: "paint", exploration_target, environment,
                    boost_area_coords, field, next_puyos, params }
server -> client: { type: "paint_progress", percent }   (深さ1段ごと)
server -> client: { type: "paint_result", plans }
server -> client: { type: "done" }
```

評価は rayon で並列化する (`par_iter().map().collect()` は**入力順を保つ**ので、
そのまま逐次版と同じ並びになる)。なぞり探索と同じく探索ごとの専用スレッドプールで
走らせ、`abort` で打ち切れる。

**幅は `params.precision` からサーバー側が導く**。クライアントは精度しか送らないので、
wasm とネイティブで幅が食い違う余地がない。逐次版との一致は
`paint_parallel_matches_sequential_search` テストで担保している。

## 10.4 UI で決めたこと

- 「塗探索」は**JS探索法を選んでいるときは出さない**（JS実装には塗り探索が無い）。
  超高精度は Rustバックエンドのときだけ出す（wasm では現実的な時間で終わらない）
- 塗り案の行にホバーすると盤面の塗るマスをハイライトする。モーダルはオーバーレイ無しで
  脇に寄せ、**盤面を隠さない**
- 多段塗り（紫→青→消し）は「適用してもう一度塗探索を開く」で自然に実現される。
  適用の取り消しは1手分だけ持つ

### 古い結果を握り続けないための指紋

探索結果と取り消し履歴は、**それがどの入力に対するものか**を指紋
（`paintSearchSignatureOf` / `boardSignatureOf`）で持つ。

| 指紋 | 含めるもの | 効く場面 |
|---|---|---|
| 探索結果 | 盤面・消し方のルール・ブーストエリア・探索対象・塗り設定 | 結果表示中の盤面編集、探索中の設定変更 |
| 取り消し | 盤面だけ | 塗ったあとに別の編集をしてからの取り消し |

指紋が合わない結果は表示にも適用にも使わない。個々のアクションに無効化処理を撒くより
漏れにくい。なぞり途中の `traceCoords` は結果に影響しないので**含めない**
（なぞりかけで結果が消えると鬱陶しいため）。

> **中断は指紋を変えない**ので、この仕組みでは弾けない。中断の扱いは別建てで、
> ドライバは await のたびに中断を見て、アクションは自分の AbortController が現役の
> ときだけストアを更新する。また wasm の評価は同期的に走りきるため、中断は
> ワーカー呼び出しとレースさせて terminate で落とすしかない
> （await 前後の判定だけでは、押したあともチャンク1つ分計算し続ける）。
